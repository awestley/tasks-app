# API contract

All application resources live under `/api/v1` and belong to the authenticated user. Bearer credentials or an HttpOnly session cookie are required. Cookie writes require the configured Origin. Invalid credentials return 401, missing or other-user resources 404, invalid input 422, stale task versions 409, request bodies over 300 KB 413. No cross-user IDs are accepted. Due dates must fall between the years 1900 and 2999. Responses describe what is stored: a task whose schedule no longer validates, for example after a time zone rule change, stays readable, and PATCH returns 422 until the schedule is corrected.

- GET /me: profile.
- GET/POST /projects; GET/PATCH/DELETE /projects/{id}: project management. Every project has a `space`, `personal` (the default) or `work`; GET /projects takes an optional `space` filter. PATCH changes only the fields it receives, and changing a project's space moves its tasks with it. Deleting a project moves its tasks into Inbox.
- GET /tasks: paginated tasks, with `offset`, `limit` (max 200), optional `q`, `project_id` (`inbox` for tasks without one), `space`, `completed`, `label`, `due_before`. For ranked search that also matches checklist items and labels, use GET /search. Dates use ISO calendar dates, interpreted in the user's local calendar.
- GET /tasks/revision: a value that changes whenever a task is added, edited or deleted, so a client can skip downloading an unchanged list. It is the task count and the latest `updated_at`, which a client can also work out from the tasks it holds.
- POST /tasks: title, description, project_id, space, due_date, priority (1 urgent through 4 normal), labels, checklist, recurrence (daily, weekly, monthly or null). A task in a project is always in the project's space, whatever `space` says. `completed` and `completed_at` restore a deleted task as it was.
- PATCH /tasks/{id}: edits require `version` from the last read. Atomic compare-and-swap prevents lost updates. Changing only `space` takes the task out of its project into the other space's Inbox. `completed: false` with `undo: true`, right after completing, also removes the recurring successor that completion created, if it has not been changed since.
- PATCH /tasks: one change for up to 100 tasks, as selecting several tasks in the apps does. The body is `{tasks: [{task_id, version}], changes}`, where `changes` may hold `completed`, `due_date`, `due_time`, `priority`, `project_id` (null for Inbox), `space` and `labels`. Each task is changed on its own, exactly like PATCH /tasks/{id}, so one stale version does not stop the rest. The response is `{changed, failed, results}`, with each task's new `version`, or the `status` (404, 409 or 422) and `error` its own request would have returned. Invalid requests, such as an empty list, a repeated task or an unsupported field, return 422 as a whole.
- POST /tasks/delete: `{tasks: [{task_id, version}]}`, up to 100, deleted one by one like DELETE /tasks/{id}, with the same response.
- POST /tasks/{id}/complete: requires version, completes once and creates the next occurrence when recurring. Restoring an occurrence does not recreate its already generated successor.
- DELETE /tasks/{id}?version=N: version-checked permanent deletion.
- GET/POST /tokens; DELETE /tokens/{id}: create/revoke 90-day personal access tokens, disclosed only once. Tokens cannot mint additional tokens or delete the account.
- GET /sessions; DELETE /sessions/{id}: list signed-in devices and end another device's session. Requires session credentials. The current session ends through POST /auth/logout.
- DELETE /me: revoke Apple authorization and delete account data. Requires session credentials.
- GET /auth/config: public provider and local-development availability.
- POST /auth/dev; POST /auth/dev/native: local development workspace, only when `DEV_LOGIN=true` outside production (404 otherwise) and only from a loopback address (403 otherwise). The browser route requires the configured Origin and sets the session cookie. The native route refuses any request carrying an Origin header and returns a native bearer session.
- GET /auth/apple/start: start browser flow with stored state, nonce and browser-binding cookie.
- POST /auth/apple/callback: consume one-time state, exchange code, validate issuer/audience/expiry/signature/nonce, set session.
- POST /auth/apple/challenge; POST /auth/apple/native: native one-time nonce + authorization code exchange. Token returned only to native client. The challenge answers 503 when Apple is not configured and 400 for a bundle ID outside `APPLE_NATIVE_CLIENT_IDS`. An account outside `ALLOWED_APPLE_ACCOUNTS` receives 403, or `auth_error=denied` in the browser flow.
- POST /auth/logout: revoke current credential and clear cookie.

OpenAPI is generated from the same validated schemas used by the server and saved to `docs/openapi.json`. API tokens work with the MCP stdio adapter. The web app follows server-sent events and refreshes when focused, downloading tasks only when the revision has changed. An event stream ends when the session or shell token that opened it ends, and a client with a valid session reconnects. Native clients refresh on activation. Every server publishes the schema at `GET /api/v1/openapi.json` without authentication, and an interactive reference at `/docs`. The reference page bundles Swagger UI into the web build, so it loads no third-party scripts. Its requests use the browser session when signed in, or a token entered under Authorize. `docs/openapi.json` holds the same schema.

## Links and references

Items are named across apps by `pc://<app>/<type>/<id>` references (the shared app contract). This app owns `pc://tasks/task/<id>` and `pc://tasks/project/<id>`; tasks and projects return theirs as `ref`.

- GET/POST /tasks/{id}/links; DELETE /tasks/{id}/links/{link_id}; the same under /projects/{id}: a link has `ref` (a reference, or null for a plain web page), `title` (up to 200 characters) and `url`. POST takes `ref`, `url` or both; a pasted Notebook or Tasks address is stored as its reference, and a known reference gets its address. Posting a reference the owner already links to updates that link and returns 200. At most 50 links per owner. URLs must be HTTPS, except localhost. Links do not change a task's version. Deleting a task or project deletes its links; a recurring task's next occurrence copies them. GET /tasks/{id} includes `links`.
- GET /references?target=<ref>: `{items}`, the caller's tasks and projects with a stored link to the target, and tasks whose description links to or embeds it, in the app contract's summary shape (`ref`, `type`, `title`, `subtitle`, `url`, `updated`, `version`).
- GET /resolve?ref=<ref>: the same summary for one of this app's tasks or projects; 404 for anything else.

## Agent

GET /agent reports whether the agent is configured and which other MCP servers it uses. POST /tasks/{id}/agent-runs with an optional `instruction` (up to 2000 characters) starts a run and returns 202; 503 when unconfigured, 409 while another run of the account is queued or running. GET /agent-runs/{id} and GET /tasks/{id}/agent-runs (latest 10) return `status` (queued, running, done, failed), `summary`, `actions` (server, tool, short input and result, ok) and `error`. The run's credential has kind `agent`: like a personal token it cannot manage credentials or the account, it lasts at most 15 minutes, and it is deleted when the run ends. Agent credentials are not listed as devices.

## MCP transport

`/mcp/` accepts Streamable HTTP using a bearer credential. Cookie-only requests are rejected. The endpoint implements the official MCP SDK protocol and exposes tools rather than a hand-written JSON-RPC approximation. Its tools call the API in process with the caller's credential, so every call passes the same authentication, validation and middleware as any client, and needs no address. Stdio runs the same tools against `TASKS_API_URL` with `TASKS_TOKEN`. Errors report the API's own message: FastAPI's `detail` (or the first validation error) or the search contract's `error` code. `update_tasks` and `delete_tasks` apply one change to up to 100 tasks, each with its own version, and report each outcome, so one stale version doesn't stop the rest. HTTP MCP currently requires client-configured tokens; OAuth authorization discovery is not implemented.

## Task checklists

Tasks include `checklist`, an ordered array of up to 100 items. Each item has a stable `id` (1-64 letters, digits, underscores or hyphens), `title` (1-500 characters), and `completed` boolean. New items may omit `id`; the server generates one. Duplicate IDs and blank titles are rejected. Omitted checklist fields preserve existing items on PATCH; supplying an array replaces the checklist and supplying `[]` clears it. Null is invalid. All changes use the task's existing version check.

Completing a task checks every checklist item atomically. Reopening the task preserves those checkmarks. Unchecking an item on a completed task is rejected unless the same request also reopens the task. Recurring successors copy item titles and IDs with all items unchecked. Checklist IDs are scoped to their task. Checking the last item does not automatically complete the task. A checklist item is not a standalone task and has no separate due date, project, priority or recurrence.

## Quick entry and reminders

`POST /api/v1/tasks/parse` accepts `text` and an IANA `time_zone`, returning a parsed title, optional scheduling/project/priority fields, labels and recognized phrases without saving. Project lookup is scoped to the caller. The `parse_task` MCP tool uses the same endpoint. Clients show the preview before applying it. Standard task creation accepts explicit fields and does not silently parse titles.

Tasks now include optional `due_time` (HH:MM), `time_zone` (IANA, UTC default for API clients), and `reminder_minutes` (null or an integer 0 through 10080). A time requires a date; a reminder requires both. PATCH omission preserves fields; null clears the time or reminder, but not the time zone. Clear dependent fields together when removing a date. Existing task version checks apply to schedule edits. See [reminder semantics](reminders.md) for DST, recurrence and delivery guarantees.

Tasks also include `alert_style` (`notification`, the default, or `alarm`) and read-only `snoozed_until` (UTC, or null). `GET /api/v1/tasks/{id}` returns one task. `POST /api/v1/tasks/{id}/snooze` accepts either `minutes` (1 to 10080) or `until` (ISO 8601 with an offset), at most 7 days ahead, without a version; it rejects completed tasks and increments the version. `GET`/`PUT /api/v1/notifications/settings` reads or replaces `summary_time` (HH:MM or null), `summary_zone` (IANA), `overdue_minutes` (30, 60, 120, 240 or null) and `time_sensitive_priority` (0 off, 1 urgent, 2 urgent and high). `PUT /api/v1/push/subscriptions/{id}/alarms` replaces the AlarmKit alarms an Apple device has armed, as up to 64 `{task_id, at}` entries; registering the same device again keeps them. The `snooze_task` MCP tool and the `alert_style` task field are available over MCP.

`GET /api/v1/push/config` returns configured provider flags and the public VAPID key. `GET/POST /api/v1/push/subscriptions` lists or registers caller-owned devices; `DELETE /api/v1/push/subscriptions/{id}` removes one. Web registration accepts kind=web, endpoint, p256dh, auth, and optional name. Native registration accepts kind=apns, token, allowed topic, sandbox boolean, and optional name. Provider identity is unique; repeated registration updates the current user's device, and another user's registration returns 409. Up to 20 devices are permitted. Response bodies never expose device tokens or encryption secrets. Unconfigured providers return 503 on registration; invalid destinations or keys return 422. Arbitrary Web Push hosts, local network destinations and unrecognized native app identifiers are rejected.
